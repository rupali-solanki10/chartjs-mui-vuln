Component Architecture & Data Flow

High-level summary

This is a React + TypeScript single-page app (Vite) that visualizes a large vulnerabilities JSON as charts and a table. The dataset is loaded at runtime (not bundled) and parsed off the main thread using a Web Worker. A central React context (DataContext) exposes the dataset and filtering helper(s). Charts and the table consume filtered results. Table selection + comparison are owned by VulnTable and reported to Dashboard.

Key files and responsibilities

  • src/types.ts

    Domain types: Vulnerability, Image, Metadata, FilterState, etc. Single source of truth for shapes.

  • src/workers/dataWorker.ts

    Loads /data.json (runtime fetch) and posts parsed result back. Worker fallback logic present in DataContext for environments where worker can't be used.

  • src/context/DataContext.tsx

    Loads raw data (worker or fetch), computes firstImage and flattens vulns. Builds precomputed indices: bySeverity, byOwner, byKaiStatus, and ports to accelerate filters. Exposes getFilteredVulns(filters: FilterState), getVulnByCve(cve), loading, error.

  • src/utils/dataUtils.ts

    Helper transformations: flattenVulns, aggregateSeverityCounts, topPackagesByVulnCount, timeSeriesByMonth, cvssBuckets, getFixableVulns, countRiskFactors, systemVsUserBySeverity, filterVulns.

  • src/pages/Dashboard.tsx

    Orchestrates layout: FilterControls, charts, VulnTable, ComparisonDrawer. Receives selection callbacks from the table.

  • src/components/VulnTable.tsx

    Renders table, sorting, selection. Owns selection state (selectedCves) and exposes onSelectionChange and onRequestCompare. Implements CSV export (escaped + UTF-8 BOM). Toolbar layout tweaks applied.

  • Chart components

    Examples: SeverityChart.tsx (Pie), TimeSeriesChart.tsx, TopPackagesChart.tsx, RiskFactorsChart.tsx, CvssScatter.tsx. They consume filtered vulns and use Chart.js option typing (ChartOptions<T>).

Data flow (sequence)

  1. Browser loads the app (index page).
  2. DataContext initializes and tries to spin up dataWorker (Web Worker).
    • Worker fetches /data.json and posts parsed JSON back.
    • If worker unavailable, DataContext falls back to main-thread fetch/parse.
  3. On receiving raw data, DataContext finds firstImage, flattens vulnerabilities, and builds indices (bySeverity, byOwner, byKaiStatus, ports).
  4. Components call getFilteredVulns(filters). Context does index intersections first and applies text/date/port tests only to candidates.
  5. Charts receive filteredVulns and compute datasets via dataUtils.
  6. VulnTable receives filteredVulns and handles selection/export/compare flows; selection emits events to Dashboard.

Contracts (APIs / Props / functions)

  • DataContext
    • Exposed: loading: boolean, error: Error | null, firstImage: Image | null, getFilteredVulns(filters: FilterState): Vulnerability[], getVulnByCve(cve: string).
  • VulnTable props
    • vulns: Vulnerability[]
    • onSelectionChange?: (selectedCves: string[]) => void
    • onRequestCompare?: (selectedCves: string[]) => void

Implementation details & design decisions

  • Worker-based parsing prevents freezing the main thread. The worker fetches /data.json at runtime — the file must be served via the dev server or available at that path in production.
  • Index-driven filtering: building Sets for each dimension and intersecting them is faster than scanning the full array for every filter change.
  • Text and date filters are applied after candidate reduction to limit expensive checks.
  • Chart.ts typing issues handled by using ChartOptions<T> and as const for literal values.
  • CSV export includes UTF-8 BOM for Excel compatibility and escapes fields.

Edge cases & failure modes

  • Missing /data.json: DataContext fallback exists but app shows error if missing.
  • Worker unavailable (CSP/older browsers): fallback to main thread might freeze UI for very large files.
  • Very large dataset memory pressure: the app holds the full array in memory; consider streaming, pagination, or server-side filtering for huge data.
  • Invalid date formats: the code skips invalid dates but tests should cover this.

Performance notes & bottlenecks

  • Strengths: Worker parsing + index-driven filtering reduce UI freezes and filtering latency.
  • Improvements: compress data.json on server (gzip/Brotli), add debounce to text inputs, use table virtualization (react-window) for very large visible row counts.

Recommended tests (priority)

  1. Unit: DataContext.getFilteredVulns – validate date range, port, owner, severity, text filtering and combined filters.
  2. Worker fallback: simulate no worker and ensure fallback fetch works.
  3. VulnTable: selection events, onRequestCompare, CSV export formatting & selected/visible rows.
  4. dataUtils: aggregation functions correctness (severity counts, top packages, time series).

Quality gates & verification checklist

  • Build locally: npm install and npm run dev.
  • Run TypeScript checks: tsc and linter.
  • Run unit tests (add Vitest/Jest) for the items above.
  • Smoke test: verify data loads, filters update charts & table, table selection opens comparison drawer, CSV export valid.

Suggested incremental improvements

  • Add Vitest + tests for filtering, selection and CSV export.
  • Add virtualization to VulnTable for large visible rows.
  • Add debounce (200–300ms) to text filters.
  • Consider server-side search or IndexedDB for massive datasets.
  • Expose an option to export selected rows vs shown rows.

Where to look

  • src/utils/dataUtils.ts — transforms

Developer checklist to run locally

  1. Ensure public/data.json is present and reachable at /data.json.
  2. Install dependencies and run the dev server locally to validate worker and UI.
  3. Run TS/lint and tests after adding them.
